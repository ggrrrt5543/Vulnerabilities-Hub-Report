# Руководство по адаптации и внедрению

## 1. Подготовить отдельный стенд

1. Получить разрешение владельца системы и определить допустимые проверки.
2. Сохранить резервную копию БД и убедиться, что восстановление работает.
3. Зафиксировать фактические схему БД, формат токенов, роли и политику публичных профилей.
4. Развернуть изменения на стенде с тестовыми аккаунтами; не копировать рабочую переписку.
5. Установить зависимости по инструкциям в README. `.env.example` — шаблон, а не готовые настройки; автоматическая загрузка `.env` в примерах не реализована.

Нельзя просто заменить существующий обработчик Hub Flask- или Express-примером: серверный стек и модель данных Hub здесь неизвестны. Сначала перенесите принцип проверки прав в существующую архитектуру.

## 2. Согласовать данные и авторизацию

Пример сообщений ожидает следующие таблицы:

| Таблица | Поля |
| --- | --- |
| `messages` | `id`, `chat_id`, `text`, `author_id` |
| `chat_members` | `chat_id`, `user_id`; составной первичный ключ |
| `chats` | `id`, `kind` |

Пример профиля ожидает `profiles(public_id, user_id, first_name, is_public)`. `user_id` — внутренний идентификатор владельца, согласованный с JWT `sub`; он не обязан совпадать с `public_id`.

Перед миграцией членства проверьте дубликаты, удалённых участников и целостность ссылок. Восстанавливайте членство только из достоверных данных — не предоставляйте всем доступ для «обратной совместимости». Типы идентификаторов, внешние ключи и индексы необходимо согласовать с реальной БД.

Для PostgreSQL возможная миграция **после проверки схемы**:

```sql
ALTER TABLE profiles
    ADD COLUMN is_public BOOLEAN NOT NULL DEFAULT FALSE;
```

Это пример, не готовая идемпотентная миграция. Если поле уже существует, проверьте его тип, NULL и значение по умолчанию. Создание первичного ключа `chat_members` требует отдельной миграции с учётом блокировок и существующих ключей. Автоматических миграций рабочей БД в репозитории нет.

## 3. Перенести контроль доступа

### Сообщения и метаданные

Фабрика `fixes/idor_messages_flask.py:create_app(engine, jwt_secret, session_is_active)` создаёт учебное приложение. Создавайте таблицы через миграции, не через `create_all()` в рабочей среде. Последний используется только в тестах.

- Извлекайте пользователя из проверенной сервером сессии, не из параметров клиента.
- Проверяйте членство до чтения и не возвращайте данные постороннему.
- Ограничьте `skip` диапазоном 0–100000, `take` диапазоном 1–100.
- Используйте стабильный порядок; для больших историй предпочтительнее курсорная пагинация.
- Возвращайте только нужные поля метаданных, без адресов владельца по умолчанию.
- В реальном коде согласуйте проверку членства и чтение с транзакционной моделью; при строгих требованиях используйте запрос, ограниченный правами пользователя, и подходящую изоляцию. Тесты не доказывают отсутствие гонок отзыва членства в PostgreSQL.

### Профили

`fixes/idor_profile_express.js:createApp` принимает `pool`, `jwtSecret`, `issuer`, `audience`, `sessionIsActive`.

- Владелец определяется по `profiles.user_id = JWT.sub`.
- Чужой профиль доступен только при `is_public = TRUE`.
- По умолчанию возвращаются лишь `public_id` и `first_name`.
- Отсутствующий и недоступный профиль дают одинаковый `403`.
- Функция `sessionIsActive` должна обращаться к общему хранилищу сессий. Подстановка `() => true` допустима только в изолированном тесте.

Параметры SQL передаются отдельно от запроса. Не добавляйте строковую интерполяцию идентификаторов из запроса клиента.

## 4. Подключить восстановление пароля

`fixes/enum_fix_flask.py:create_app(enqueue_request)` требует реальную функцию постановки задания в очередь.

HTTP-обработчик ставит в очередь любой синтаксически допустимый адрес, независимо от существования аккаунта. Рабочий процесс должен отдельно:

1. Найти пользователя с той же нормализацией адресов, что при регистрации.
2. Создать криптографически стойкий одноразовый код с коротким сроком действия.
3. Хранить защищённое представление кода, ограничить число попыток и повторную отправку.
4. Отправить письмо, только если аккаунт существует.
5. Не раскрывать наличие аккаунта через состояние задания, ошибки или метрики для клиента.

Рабочий процесс, почтовый провайдер и очередь здесь не реализованы. Без них пример не отправляет письма. Случайная задержка `sleep` не является достаточной защитой от временного анализа. Измерьте распределения времени ответов на стенде.

Для допустимых адресов ответ: `200` и «Если аккаунт существует, код отправлен». Неверный формат даёт `400`, переполнение тела — `413`, общий сбой очереди — `503`. CAPTCHA и ограничения частоты могут давать другие отказы, но не должны зависеть от существования аккаунта.

## 5. Включить ограничения частоты и CAPTCHA

В `fixes/nginx_ratelimit.conf` активны только объявления зон для контекста `http {}`. Примеры `location` намеренно закомментированы: их нужно перенести в существующий HTTPS `server {}`, настроить `upstream backend` и **включить**. Простое подключение файла не ограничивает маршруты.

- Выполните `nginx -t` на целевой машине до перезагрузки.
- Укажите `limit_req_status 429`; по умолчанию Nginx использует `503`.
- Настройте лимиты не только по IP, но и по аккаунту, в том числе на рабочем процессе отправки писем.
- Настройте `real_ip` только для доверенных прокси; не доверяйте произвольному `X-Forwarded-For`.
- Защитите маршруты регистрации аналогично; точный маршрут здесь неизвестен.

`require_captcha(secret, expected_hostname)` предназначен для reCAPTCHA v2. Передайте настоящий секрет через менеджер секретов и точное ожидаемое имя хоста без схемы. Декоратор нужно явно применить к маршруту; сам файл ничего автоматически не включает. Для reCAPTCHA v3 дополнительно проверяйте `action` и `score`. Реальный провайдер в тестах не вызывался.

## 6. Встроить жизненный цикл токенов

`TokenService` в `fixes/jwt_rotation.py` — отдельный сервис функций, а не HTTP-маршрут `/api/auth/refresh`.

- `issue_tokens(user_id)` вызывается только после полноценной проверки входа.
- `rotate_refresh(token)` атомарно заменяет активный refresh через Redis `WATCH/MULTI/EXEC`.
- `verify_access(token)` проверяет подпись, срок, издателя, аудиторию, тип и активность семьи.
- `revoke_session(access_token)` отзывает одну текущую сессию; токен должен ещё быть действителен.
- `session_is_active(payload)` проверяет состояние семьи **только после** криптографической проверки JWT вызывающим компонентом.

Пример связывания Flask с сервисом токенов:

```python
import os
import redis
from sqlalchemy import create_engine
from fixes.idor_messages_flask import create_app
from fixes.jwt_rotation import TokenService

secret = os.environ["JWT_SECRET"]
store = redis.Redis.from_url(os.environ["REDIS_URL"], decode_responses=True)
service = TokenService(store, secret)
app = create_app(create_engine(os.environ["DATABASE_URL"]), secret,
                 service.session_is_active)
```

Это не добавляет вход, refresh-маршрут, обработку ошибок инфраструктуры и HTTP-сервер для рабочей среды. Их должен реализовать основной проект. JWT этого сервиса и cookie `x-session-token` из исходного отчёта не взаимозаменяемы.

Access действует не более 15 минут, refresh-семья — не более 7 дней от входа. Ротация не продлевает абсолютный срок семьи. Повтор старого refresh отзывает **одну семью**, а не все устройства пользователя. Для выхода со всех устройств нужен отдельный индекс семей пользователя и операция массового отзыва — здесь их нет.

Одновременные запросы refresh трактуются как повторное использование и отзывают сессию. Клиент обязан сериализовать обновление токена; после сетевого таймаута может потребоваться повторный вход. Это сознательная строгая политика, а не поддержка прозрачного повтора запросов.

Согласуйте `issuer` и `audience` во всех компонентах. Секрет HMAC должен быть случайным и содержать не менее 32 байт; проверка длины не доказывает достаточную энтропию. Пример не реализует ротацию ключей подписи.

Redis должен быть общим для всех серверов, защищённым ACL/TLS и настроенным по требованиям сохранности сессий. Потеря записей в этой модели закрывает сессии; восстановление устаревшего снимка требует отдельного плана, чтобы не вернуть старые разрешения. При ошибке Redis запрещайте доступ, не включайте обход проверки. Для браузерных cookie отдельно требуются `Secure`, `HttpOnly`, подходящий `SameSite` и защита CSRF.

## 7. Адаптировать Socket.IO

`fixes/ws_secure.py:create_server` принимает асинхронные функции проверки токена, проверки членства и записи сообщения, а также список разрешённых источников.

`lookup_user_by_token` должна проверять подпись, срок, отзыв токена и блокировку пользователя. Ошибки инфраструктуры не должны становиться успешным входом. `save_message` должна повторно обеспечить право записи в согласованной с проверкой членства транзакции.

Клиент использует пакет подключения Socket.IO `auth: { token: ... }`, не URL. Это отличается и от произвольного WebSocket-протокола, и от отдельного события `auth` в исходном примере.

Пример повторно проверяет токен и членство на каждой отправке, ограничивает текст и не доверяет `authorId` клиента. Подписки `joinChat`, рассылка, вложения и доставка сообщений здесь не реализованы. Если они нужны, нельзя оставлять исключённого участника в комнате с продолжающейся рассылкой.

Разрешённый `Origin` не заменяет аутентификацию. Согласно документации Socket.IO, запрос без `Origin` не ограничивается этой проверкой; токен остаётся обязательным. Для строгой политики браузерного Origin добавьте отдельную проверку и согласуйте её с мобильными клиентами.

## 8. Проверить и вводить постепенно

| Сценарий | Ожидание |
| --- | --- |
| Запрос без токена, с истёкшим или отозванным JWT | `401` |
| Сообщения и метаданные чужого чата | `403`, без данных |
| Собственный чат | Доступ только к разрешённым полям |
| Закрытый чужой профиль | `403` |
| Свой или разрешённый публичный профиль | `200`, ограниченные поля |
| Неверная пагинация | `400` |
| Два допустимых адреса восстановления | Одинаковое сообщение и сопоставимые задержки |
| Повтор refresh | Отказ, отзыв всей соответствующей семьи |
| Параллельный refresh | Не более одной выдачи, последующий отзыв семьи при обнаружении повтора |
| Подмена автора Socket.IO | Автор берётся из серверной сессии |
| Удаление участника | Следующие чтения и отправки запрещены |
| Превышение лимита Nginx | `429` после настройки и включения |

После локальных тестов нужны интеграционные проверки с настоящими PostgreSQL, Redis, Nginx, очередью, почтой и клиентом Socket.IO. На рабочую систему изменения вводятся отдельно, с наблюдаемостью и планом отката. Автоматического сканирования действующего Hub эта инструкция не предусматривает.
